# Card Tokenization (RBI Mandate)

## What is tokenization
Tokenization replaces a card's 16-digit PAN (Primary Account Number) with a unique, non-reversible token. The token is specific to a combination of card + merchant + device. Even if the token is compromised, it cannot be used elsewhere.

## RBI mandate timeline
- **Sep 2021**: RBI directed that no entity in the payment chain (merchant, PA, PG) can store actual card data.
- **Oct 2022**: Enforcement date. All stored card data must be purged. Only card networks and issuers can store PANs.
- **Compliance**: Merchants and PAs must tokenize cards through the card network's tokenization service (Visa VTS, Mastercard MDES, RuPay tokenization).

## How it works

### Token provisioning (one-time)
1. Customer initiates first payment on a merchant's platform.
2. Customer consents to save card for future use.
3. Merchant/PA sends tokenization request to card network.
4. Network creates a token linked to: card PAN + merchant ID + device/channel.
5. Token is returned to merchant. Merchant stores only the token + last 4 digits of card + card network + expiry (for display purposes).
6. Actual PAN is stored only at the network and issuer.

### Token usage (recurring payments)
1. Customer selects saved card (shown as "ending in XXXX").
2. Merchant sends token + cryptogram to acquirer.
3. Acquirer sends to network.
4. Network de-tokenizes to actual PAN and routes to issuer.
5. Issuer processes as normal card transaction.
6. Response flows back through the same chain.

## Impact on merchants

### Positive
- Reduced PCI-DSS scope (no card data storage = fewer compliance requirements).
- Lower risk of data breach liability.
- Tokens have equal or better authorisation rates than raw PANs (per Visa/MC data).
- Returning customers can still "one-click pay" using saved tokens.

### Challenges
- **Token portability**: Tokens are merchant-specific. If a merchant changes acquirers, tokens may need to be re-provisioned.
- **Multi-device**: Token is device-specific. Customer saving a card on mobile won't see it on desktop.
- **Guest checkout**: Tokenization only applies to saved cards. Guest/one-time transactions use the full card for that transaction but don't store it.
- **Recurring payments**: Existing mandates (subscriptions) needed token migration. Most were migrated by networks automatically.

## What merchants must NOT store
- Full card number (PAN)
- CVV/CVC
- PIN
- Track 1/Track 2 data from magnetic stripe
- Sensitive authentication data

## What merchants CAN store
- Token (the substitute value)
- Last 4 digits of card number (for display)
- Card network (Visa/MC/RuPay)
- Card type (debit/credit)
- Expiry month/year
- Cardholder name (if needed for communication)

## POS terminal tokenization
- For physical POS, tokenization applies differently: the terminal reads the card directly and sends data to acquirer. Terminal does not store card data between transactions.
- Contactless (tap) transactions use a device-level token generated by Apple Pay/Google Pay/Samsung Pay — these are already tokenized by the mobile wallet.
- The merchant's POS system should not log or store full card data in any transaction log or receipt (only last 4 digits on printed receipt per RBI/PCI rules).
